## 1. 結論

**差別化の軸は「知名度を差し引いて町を選ぶ」ことの一点。** 競合はどこも口コミの量と評価で推薦していて、口コミの少ない町は構造的に上がらない。この軸を、見せ方・信頼性・地域側の3方向から補強する。

| # | 打ち手 | 観点 | 効く審査ポイント | 重さ |
| --- | --- | --- | --- | --- |
| 1 | **スポットライト地図＋「人気順 ⇄ 穴場度順」切り替え:** 切り替えると、光が有名地から知られていない町へ移る | 見せ方 | ① 課題設定のリアルさ ② インパクト | M |
| 2 | **地図で見せる「考え中」:** 条件に合わない町が、理由付きで順に暗くなる | 見せ方 | ② インパクト ③ 完成度 | S |
| 3 | **根拠となる「元の声」を付ける:** 推薦文ごとに根拠の件数と原文を付け、タップで確かめられる。データにないことは言わせない | 信頼性 | ② AI である必然性 ③ 完成度 | M |
| 4 | **件数で補正した穴場度（ベイズ平均）と、確かさの表示（例: n=4・参考値）** | 信頼性 | ③ 完成度（質疑対策） | S |
| 5 | **町向けレポート「知られていない強み」:** 行く前は知らなかった人が満足した点を町に返す | 地域側 | ④ 拡張性 | M |

**デモの流れ（1本につながる）:** 相談 → AI が読み取った条件をタグで表示 → 地図で町が順に暗くなる（2）→ 3町が光る → 「人気順」に切り替えると光が有名地へ、戻すと穴場へ（1）→ カードに「知らなかった人の声」（3・4）→ 1日プラン → フィードバック → 町向けレポート（5）

## 2. 競合: まだ誰もやっていない「空白」

| 空白 | 根拠 |
| --- | --- |
| **知名度を差し引いて町を選ぶ** | 大手の推薦の根拠は口コミの量と評価（Google は3億以上の場所、Tripadvisor は10億件以上の口コミ）。Google マップの「マップに相談」は「穴場」を「高評価」とほぼ同じ意味で扱っていたと報告されている |
| **行き先が決まる前の相談から町を出す** | NAVITIME・Layla は目的地の入力が前提。Mindtrip は SNS 動画などから旅程を作るので、すでに投稿された場所しか出ない |
| **「ここなら大丈夫」と思える根拠を添える** | 生成 AI の宿の提案を採用しなかった理由は「口コミが不安」35.4%、「情報が少ない」26.1%。「AI の提案に誤りがありそう」は 2.2% だけ（宿研 2026）。問題は AI の精度ではなく、安心できる根拠がないこと |

### 主なサービスの比較

| サービス | 入力 → 出力 | 知られていない地域を出せるか |
| --- | --- | --- |
| Google「マップに相談」 | 自然文 → 口コミ評価付きのカード | 穴場を「高評価」扱いにしがち |
| Google AI Mode Canvas | 自然文 → 編集できる旅程 | 実験機能。日本語で使えるかは未確認。予約へ誘導する |
| Mindtrip | チャット・SNS の素材 → 地図と連動した旅程 | SNS に出た場所に偏る【推測】 |
| Layla（Expedia） | 日程・目的地・予算 → 料金付きのプラン | 目的地の入力が前提 |
| Tripadvisor AI | 興味・日程 → 旅程 | 口コミの多い場所が有利 |
| Booking.com | 自然文 → 条件フィルタ（どの条件を適用したかが見える） | 宿だけが対象 |
| NAVITIME Travel AI | 出発地・目的地 → 順路付きの1日プラン | 目的地が前提で、定番を選ぶ方向 |
| じゃらん「トリップAIコンシェルジュ」 | 自治体・事業者向けの問い合わせ AI | もう来る気の人にしか効かない |

### 真似すべき点と避けるべき点

- **真似すべき点:**
  - チャットと地図の連動（Mindtrip）
  - AI が読み取った条件をタグで見せる（Booking.com）
  - 近い場所どうしで1日を組む（Tripadvisor）
- **避けるべき点:**
  - 「穴場＝高評価」と同じにする
  - 初回に長い質問に答えさせる（Wanderboat は15〜20分）
  - 予約をゴールにする【推測: 予約できる商品の少ない町を推す理由がなくなる】
  - 出典のない AI の断定

## 3. 見せ方

### スポットライト案の評価

- **技術としては新しくない。** 地図の外側を暗くする Leaflet のプラグイン（Leaflet.snogylop、Leaflet.Mask）や、塗り分け地図は昔からある
- **新しいのは使い方。** 「並べ方を切り替えると、光が有名地から知られていない町へ移る」ことで主張を見せる例は見つからなかった。Google の「マップに相談」・Mindtrip・Airbnb は、どれもピンとリストで結果を出す方式
- **考え中の演出:** 途中経過を見せると利用者が待ってくれ、信用も増す（Perplexity の知見）。これを文字ではなく地図の上でやる例は見つからなかった。暗くなるたびに「車なしで行けない → 3町」のような短い理由を添える

**見送り:** スクロールで話が進む演出（NYT 型）や Google Earth 型のツアー。発表のスライドと役割がかぶり、7分では足りない【推測】

### 実装上の注意

| 項目 | 内容 |
| --- | --- |
| 境界データ | 国土数値情報 N03（行政区域）。出典表記が必要。1つの町が複数の図形に分かれることがあるので、行政区域コード（N03_007）で1町1図形にまとめる |
| 軽量化 | mapshaper で茨城県だけを取り出し、`-simplify 10% keep-shapes` で軽くする。隣の町との境界が保たれ、隙間ができない。GeoJSON はソースに同梱する |
| 描画 | 44個の図形なら SVG で十分。塗りの透明度に CSS の transition をかければ、「順に暗くなる」演出を安く作れる |
| 背景地図 | 背景は単色の暗い色にして、市町村の形だけを描く方式を基本にする。通信がなくても動き、スポットライトも一番よく見える。CARTO Dark Matter は「あれば重ねる」扱いにする（出典表示が必要。API キーの要否は要確認） |
| 使いやすさ | 暗くした町もうっすら見せ、クリックできるようにする。OS で動きを減らす設定が有効なときは、アニメーションを止める |
| 発表 | 山場は「切り替えると光が移る」1回に集中させる。会場の通信トラブルに備えてデモの録画を必ず用意する |

## 4. 信頼性

### 分かった事実

- **やらせ:**
  - Tripadvisor では、2024年の投稿の約8%（270万件）が偽の口コミだった
  - Google マップは2024年、違反した口コミを2.4億件以上ブロックまたは削除した
  - 日本では2023年10月から、ステマが景品表示法の規制対象になった
- **評価の偏り:**
  - 最初に高評価が1つ付くだけで、最終的な評価が平均25%上がった（Science 2013）
  - 口コミの評価は、極端な感想の人ほど書くため J字型に偏る
- **AI と出典:**
  - AI 検索は出典を60%以上で間違えた
  - 引用が付いているだけで信頼は上がるが、確かめて中身が合わないと下がる（AAAI 2025）
  - Google の AI による口コミ要約は、元の口コミへのリンク表示が義務になっている
- **似た指標:**
  - JTB の「地域パワーインデックス」は満足度と認知度を測るが、企業向けで公開されていない
  - 北海道は「行く前の期待」と「実際の満足」の差を見ている

### 穴場度の式の弱点と改善案

| 弱点 | 改善案 |
| --- | --- |
| 件数が少ないと点数が大きくぶれる | 満足度はベイズ平均 `(C×全体平均＋評価の合計)/(C＋件数)`（C=5前後）にする。知っていた人の割合も同じように補正する |
| 満足度が低くても、知名度がゼロなら上位に来る（満足度2・知名度0 ＝ 満足度5・知名度3） | 補正後の満足度が3.5未満の町は候補から外す【推測】 |
| 知名度を来た人だけに聞いている（来た人はどこかで町を知っている） | 設問を「行こうと決める前から名前を知っていたか」にする。来ていない人の認知は将来、外部の調査で補うと説明する |
| 人気が出るほど穴場度が下がる | 設計どおり。穴場を卒業した町は人気順の側に移る、と説明できる |

### フィードバックの歪みを防ぐ

- 評価を入力する画面では、その町の今の点数を見せない（最初の高評価に引っ張られる偏りの対策）
- 同じ人が同じ町を評価できるのは1回まで
- 地元の人や関係者には申告してもらう

### 想定される質疑と答え

| 質問 | 答え |
| --- | --- |
| AI が嘘の町やスポットを出さない？ | 候補は自分たちのデータにある町だけ。根拠となる声を付けられない文は出さない |
| やらせで穴場度を上げられるのでは？ | 次の4つで防ぐ: 件数の補正、1人1回まで、関係者の申告、評価するときに今の点数を見せない |
| 件数が少ない町はどうする？ | ベイズ平均で補正し、「n=3・参考値」のように確かさを表示する |
| 知名度を来た人に聞くのはおかしいのでは？ | 弱点だと認める。設問を工夫していることと、将来は外部の認知度調査と組み合わせることを答える |
| JTB の調査と何が違う？ | JTB は企業向けで非公開。私たちは旅行者に直接届け、フィードバックで点数が更新され続ける |

## 5. 地域側の価値と続けられる仕組み

### 茨城県の実データ（2025年 観光客動態調査）

- 入込客数は延べ6,258万人、観光消費額は4,482億円（4年連続で最高）
- 日帰り客が81.9%。1回の旅行で訪れる観光地点は平均1.3〜1.8か所で、報告書は「1地点のみの訪問が多数」と書いている
- **県北だけが前年比93.0%と減っている**（県央108.3%、鹿行109.7%）
- その場所を何で知ったか: 知人31.7%、インターネット28.6%、SNS 8.3%

【推測】「日帰り・1か所だけ・リピーター頼み」という構図が読める。2か所目を回ってもらう余地があり、減っている県北は穴場の舞台として筋が良い

### 続かない理由と、続いている例

- **続かない理由:** 地域側に予算とデータを扱える人材がない。DMO の約8割が予算を課題に挙げている
- **国の要件:** DMO は「データの継続的な収集・分析」が登録要件。2025年のガイドライン改定で、補助金に頼らない財源の計画が義務になった
- **続いている例:** おてつたびは、地域側の掲載料を無料にし、マッチングしたときだけ手数料を取る。登録ユーザーは約8.5万人
- **比較相手:**
  - JTB と KIYONO の「AIレポーター」は、予約・販売データから自治体向けのレポートを自動で作る
  - 熱海の AI 実証は、Google 検索の表示回数が15.3倍、レポートの作成時間が1/30になった
  - どちらも「すでに来た人・知っている人」のデータで、「知らなかったのに満足した人」を切り出してはいない

### 拡張性のロードマップ案

| 段階 | 内容 | 誰が払うか |
| --- | --- | --- |
| 1. 今回 | 茨城のモックで、穴場度・1日プラン・町向けレポートの一連の流れを見せる | なし |
| 2. 実証 | 茨城県北の1エリアで、観光地のアンケートに「行く前に知っていたか」を1問足してもらう。AI を Claude API に差し替える | 観光庁の生成 AI 実証の枠、または自治体の委託 |
| 3. 展開 | オープンデータから町を取り込み、他の県へ広げる。ふるさと納税や体験の予約への送客につなぐ | 基本レポートは委託、来訪につながった分は成果報酬 |

**発表での一言案:** 「補助金が切れたら終わる観光アプリにはしない。町がもともと持っているデータ収集と財源の枠で払える形にする」

## 6. 要件定義書への反映候補

取り入れると決めた場合に変えるもの:

| 要件定義書の箇所 | 変更 |
| --- | --- |
| F5 マップ | 市町村の塗り分けとスポットライトに変える。背景は単色（通信不要）を基本にする |
| F8 考え中 | Should から Must に上げ、地図の演出（理由付きで町が暗くなる）に変える |
| F9 有名どころとの比較 | 「人気順 ⇄ 穴場度順」の切り替えに変え、Must に上げる |
| F6 フィードバック | 一行の感想欄と関係者の申告欄を足す。入力する画面では今の点数を見せない |
| 5章 計算 | 満足度と知名度をベイズ平均にし、満足度が低い町を除外する条件を足す。「件数5件未満」の扱いは n の表示に置き換える |
| 新規 | 根拠となる声の表示（打ち手3）、町向けレポート（打ち手5） |
| 7章 舞台 | 茨城県北を中心にする（入込が唯一減っている地域） |
